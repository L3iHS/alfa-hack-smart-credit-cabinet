# Умный кредитный кабинет

Прототип для хакатона Альфа-Банка 2026: предприниматель подаёт кредитную заявку, сотрудник рассматривает её, а обе роли проходят согласование условий и демонстрационное оформление в одном веб-кабинете.

Демонстрационный стенд — [biom.cloud-path.ru](https://biom.cloud-path.ru).

Исходный код — [репозиторий на GitHub](https://github.com/L3iHS/alfa-hack-smart-credit-cabinet).

Кабинет поддерживает шесть продуктов: оборотный кредит, оборудование, овердрафт, кредитную линию, инвестиционный кредит и тендерную гарантию. Все компании, финансовые данные и внешние проверки синтетические; условия не являются тарифами Альфа-Банка.

## Что можно показать

- **Клиент:** подбор продукта и нагрузки, черновик, загрузка документов, отправка, ответ на уточнение, принятие других условий и подтверждение оформления.
- **Сотрудник:** очередь, проверки, расчёт, ML-риск для двух продуктов, запрос сведений, мотивированное решение, подготовка и завершение оформления.
- **Обе роли:** сохранённые условия, история, отдельный статус сделки и скачивание условий в Markdown.
- **Аналитика:** заполнение и отправка заявки, просмотр и ответ на предложения, причины отказа и сравнение условий.
- **Необязательный помощник:** разбор потребности, ответы с источниками и сводка сотруднику; основной кабинет работает без LLM.

[Продукт и роли](docs/product.md) · [Маршрут демонстрации](docs/demo-scenarios.md)

## Запуск с нуля

Нужны Docker и Docker Compose 2.24.4 или новее. Выполните из корня полученного репозитория:

```sh
cp .env.example .env
docker compose up --build -d --wait
docker compose exec backend uv run python -m app.seed
```

[Открыть кабинет](http://localhost:8080) · [Swagger UI](http://localhost:8080/api/v1/docs) · [OpenAPI](http://localhost:8080/api/v1/openapi.json)

При первой сборке нужен доступ к реестрам образов и пакетам. После сборки основной кабинет не требует внешних банковских API, обучения или LLM. JSON выбранной модели уже включён в обычный backend-образ; ML extra и GPU для запуска не нужны. Backend применяет миграции автоматически.

### Демонстрационные учётные записи

**Для локального запуска:** пароль новых аккаунтов — `DEMO_PASSWORD` из `.env`, в примере `Demo-credit-2026!`. Доступ к публичному стенду выдаётся отдельно.

| Email | Роль и сценарий |
| --- | --- |
| `client1@example.test` | Клиент, Демо Пекарня |
| `client2@example.test` | Клиент другой компании; изоляция доступа |
| `staff@example.test` | Сотрудник |
| `demo-a@example.test` | Оборудование; сравнение низкого и повышенного риска |
| `demo-b@example.test` | Оборотный кредит; другие условия сотрудника |
| `demo-c@example.test` | Уточнение выручки |
| `demo-d@example.test` | Ручное рассмотрение |
| `demo-e@example.test` | Отказ по синтетической просрочке |

Seed создаёт компании и аккаунты, сохраняя существующие данные и пароли. Готовые заявки, документы и аналитика не создаются: они появляются при прохождении сценария.

## Полный путь за несколько минут

1. Откройте две независимые сессии браузера: клиент `demo-a@example.test` и сотрудник `staff@example.test`.
2. Создайте заявку по [короткому сценарию](docs/demo-scenarios.md#короткий-проход-всех-шести-продуктов), сохраните, приложите синтетический файл и отправьте с подтверждениями.
3. Изучите результат проверок. При ручном рассмотрении сотрудник принимает решение с причиной; клиент может принять предложенные другие условия.
4. После одобрения сотрудник нажимает «Подготовить оформление». Клиент изучает окончательные условия и явно подтверждает их.
5. Сотрудник завершает оформление. Обе роли видят «Кредит выдан», «Лимит открыт» или «Гарантия выпущена» и могут скачать сохранённые условия.

Последний шаг фиксирует **демонстрационный результат**. Юридическое подписание, перевод денег, открытие действующего лимита и настоящий выпуск гарантии не выполняются. Одобрение заявки и оформление сделки имеют отдельные статусы.

## Зачем нужны ML, правила и помощник

Правила каталога ограничивают продукт, считают платежи и проверяют обязательные условия. Подбор использует тот же расчёт, но не принимает кредитного решения.

LogisticRegression оценивает риск достижения 90 дней просрочки в первые 12 календарных месяцев. Она применяется только к оборотному кредиту и оборудованию; остальные четыре продукта рассматривает сотрудник. Модель выбрана по validation среди baseline, LogisticRegression и CatBoost. [Исторические метрики и исходные отчёты](docs/ml-training.md) относятся к синтетике и не подтверждают качество на реальных заёмщиках.

LLM помогает работать с текстом. RAG добавляет справочник и разрешённый актуальный контекст заявки; финансовые расчёты и решения выполняет код. Для включения нужен свой провайдер и ключ в закрытом environment-файле. [Настройка и проверенный профиль](docs/assistant.md#настройка-проверенного-профиля) описаны отдельно; веса LLM в поставку не входят.

## Границы демонстрации

- Реальные ФНС/БКИ, банковские интеграции и OCR не подключены. Файлы проверяются технически; финансовые показатели вводятся в форму.
- Риск — вероятность просрочки, а не одобрения. Отказа только по ML нет; правила и основания доступны в [архитектуре](docs/architecture.md).
- Аналитика считает отправку заявки и ответ на предложение; стадии сделки не включены в конверсию выдачи.
- LLM может ошибаться даже при корректной форме ответа; проверяйте источники. При отключении помощника основной процесс сохраняется.
- Нагрузка берётся из финансов этой заявки. Обязательства по другим одобренным/оформленным заявкам компании автоматически не суммируются; [учёт совокупной нагрузки](docs/roadmap.md#совокупная-долговая-нагрузка-компании) требует отдельного развития.
- Один процесс backend содержит один worker. Технические сбои требуют явного повтора сотрудником.
- PostgreSQL и файлы хранятся в постоянных томах; обычный restart их сохраняет. Для следующего показа создавайте новые заявки.
