# Подбор кредитных продуктов

Рекомендации работают отдельно от кредитного процесса: они не создают заявку,
не пишут в БД и не меняют `logistic-risk-v1` или `demo-policy-0.3`. Ответ
содержит `config_version`, чтобы клиент и поддержка понимали, по каким правилам
получен результат.

## API

Оба метода доступны с префиксом `/api/v1`.

- `GET /product-recommendations/options` — цели, типы залога и варианты срочности.
- `POST /product-recommendations` — подбор по параметрам заявки; требует сессии и CSRF.

Клиентские суммы передаются в копейках. В конфигах и внутри движка суммы
считаются в рублях через `Decimal`.

Пример запроса:

```json
{
  "purpose": "working_capital",
  "amount_kopecks": 200000000,
  "term_months": 12,
  "urgency": "normal",
  "has_collateral": false,
  "collateral_type": "none",
  "supplier_invoice_attached": true,
  "down_payment_pct": 10,
  "revenue_total_kopecks": 3000000000,
  "expenses_total_kopecks": 2000000000,
  "existing_debt_payments_kopecks": 10000000,
  "period_months": 1
}
```

Для клиента компания берётся из сессии. Сотрудник передаёт `?company_id=<uuid>`
и получает `staff_trace`; клиент этот блок не видит.

## Слои движка

1. L0 — глобальные стоп-факторы: ЕГРЮЛ, массовый адрес, дисквалификация
   директора, просрочка.
2. L1 — цель: основная или смежная.
3. L2 — eligibility: тип клиента, возраст бизнеса, ОКВЭД, кредитная история.
4. L3 — потребности: сумма, срок, залог, документы, первоначальный взнос.
5. L4 — финансовые лимиты: отношение суммы к выручке, платёж к обороту, DTI,
   прибыль.
6. L5 — ранжирование: цель, соответствие сумме и сроку, стоимость, вероятность
   одобрения, скорость.

Правила с `on_fail: adjust` могут уменьшить сумму или срок и вернуть
`counter_offer`. Если данных не хватает, возвращается `request_data` со списком
полей и действиями. Жёсткие нарушения исключают продукт.

`approval_likelihood` — эвристическая оценка для интерфейса, а не результат
ML-модели. Она не влияет на кредитное решение.

## Конфигурация

Файлы лежат в `backend/config/rules`:

- `products.yaml` — 6 продуктов, правила и pricing;
- `purpose_map.yaml` — основные и смежные продукты по цели;
- `ranking.yaml` — веса и ограничения ранжирования;
- `stop_factors.yaml` — глобальные ограничения и исключённые ОКВЭД;
- `reasons.yaml` — клиентские и служебные тексты.

При первом запросе конфиг загружается один раз и кешируется; проверяются ссылки
на продукты, `reason_code`, правила и суммы весов. Fingerprint всех файлов
используется для диагностики; при изменении конфигов процесс нужно перезапустить.

## Кабинет

В кабинет можно перенести только продукты с `cabinet_product_code`:

- `working_capital_loan` → `working_capital`;
- `equipment_loan` → `equipment`.

Остальные продукты показываются как рекомендации, но оформление для них не
подключено. При переносе сумма и срок дополнительно ограничиваются каталогом
кабинета.

## Проверка

- `cd backend && uv run pytest -q tests/test_recommendations.py`
- `cd frontend && npm run build`
- `cd frontend && npx playwright test tests/recommendations.spec.ts`

API-тесты требуют PostgreSQL и переменные окружения из `.env`, как и остальные
интеграционные тесты проекта. E2e-сценарий запускается против поднятого стека.
