# Синтетические данные кредитного риска

Генератор создаёт вымышленные компании, заявки и будущие события по кредиту. Экспорт предназначен для воспроизводимого эксперимента перед обучением; модель пока не обучена и не влияет на решения кабинета. Банковские данные и внешние API не используются.

## Сборка

Из каталога `backend` с Python 3.12 и установленным uv:

```sh
uv sync --frozen
uv run python -m app.risk build-data --output artifacts/risk-data --rows 10000 --seed 20261021
```

Отдельный запуск через Docker из корня проекта, без PostgreSQL, `.env` и HTTP-сервера:

```sh
docker build -t smart-credit-data ./backend
mkdir -p backend/artifacts
docker run --rm --network none \
  -v "$PWD/backend/artifacts:/app/artifacts" \
  smart-credit-data uv run python -m app.risk build-data \
  --output artifacts/risk-data --rows 10000 --seed 20261021
```

Результат сохраняется в `backend/artifacts/risk-data/`, который исключён из Git. Параметры по умолчанию совпадают с приведёнными. Нужно не менее 20 компаний. Существующий путь, включая файл или символическую ссылку, вызывает ошибку; для следующей сборки задайте новый каталог. Утилита рассчитана на последовательные запуски: готовые файлы собираются во временном соседнем каталоге и затем публикуются переименованием. Гарантия конкурентной публикации в один путь не предоставляется.

## Состав файлов

- `train.csv`, `validation.csv`, `test.csv`: два идентификатора, девять признаков, девять масок пропусков и метка `loan_90dpd_12m` последним столбцом.
- `observations.jsonl`: **synthetic diagnostic**, отдельный аудит исходной заявки, дат отправки и регистрации, исходной просрочки, будущего исхода и `true_probability`. Это диагностические сведения генератора; файл не является таблицей входов модели.
- `schema.json`: версии, целевое событие, календарный горизонт, типы, единицы и точные списки столбцов. Для последующего обучения используются только `feature_columns`; идентификаторы остаются метаданными.
- `report.json`: размеры частей, компании, продукты, сроки, классы, доли событий и пропуски; проверка пересечений компаний и конечности чисел. Метрик обученной модели в отчёте нет.
- `manifest.json`: версии набора, признаков, генератора, цели и каталога, seed, размер, версия Python и SHA256 остальных шести файлов. Времени запуска и пути вывода в нём нет.

При одинаковых версиях, seed, размере и окружении повтор воспроизводит файлы по байтам. Изменение seed меняет данные. Повтор на Python 3.12.10 проверен для 10 000 строк; текущие контрольные суммы находятся в манифесте конкретного набора.

## Признаки и пропуски

Признаки рассчитывает общий `build_features` в [features.py](../backend/app/risk/features.py). Финансовые суммы исходной заявки — целые копейки за завершённые месяцы; денежные расчёты выполняются через Decimal, затем готовые числовые признаки преобразуются в конечные float.

| Признак | Смысл |
| --- | --- |
| `business_age_months` | Полные месяцы от регистрации до отправки |
| `monthly_revenue_rub` | Средняя месячная выручка, рубли |
| `operating_margin_ratio` | (Выручка − операционные расходы) / выручка |
| `existing_debt_to_revenue_ratio` | Платежи по существующим долгам / выручка |
| `coverage_ratio` | (Выручка − расходы) / (существующие платежи + платёж нового кредита) |
| `overdue_days` | Известная просрочка по старым обязательствам на момент отправки, дни |
| `product_code` | Категория: `working_capital` или `equipment` |
| `requested_amount_rub` | Запрошенная сумма в рублях |
| `term_months` | Договорный срок в месяцах |

При нулевой выручке два отношения к выручке неопределены: в CSV это пустые ячейки, а соответствующие `<feature>_missing` равны 1. У присутствующего значения маска равна 0; нулевая выручка сама остаётся числом 0. Пропуски не заменяются нулями в таблице, NaN/Infinity не допускаются. Кодирование категории и обработка пропусков для обучения ещё не реализованы.

## Цель и разделение

`loan_90dpd_12m = 1`, если по рассматриваемому новому кредиту достигнуты 90 дней просрочки не позднее даты выдачи + 12 **календарных** месяцев включительно. Это не просто пропуск платежа и не текущая просрочка по старым долгам. `0` означает полное наблюдение горизонта без события либо подтверждённое окончательное погашение без такого события. При неполном наблюдении без события и погашения метка неизвестна (`None`): экспорт прерывается, а не записывает 0. Договорная дата окончания кредита сама по себе не доказывает погашение. Разметка реализована в [labels.py](../backend/app/risk/labels.py).

Для разделения уникальные `company_id` сортируются, перемешиваются локальным RNG с seed и распределяются: floor(70%) в train, floor(15%) в validation, остаток в test. Все заявки одной компании остаются вместе, порядок входа не влияет на результат; повторяющийся `application_id` запрещён. Внутри каждой части строки отсортированы по компании и заявке. Генератор сейчас создаёт одну заявку на компанию.

Train предназначен для обучения, validation — для выбора подхода и настроек. Test следует оставить для итоговой проверки; по нему не выбираются генератор, признаки и пороги. Отсутствующий класс в небольшой выборке отражается как нулевой счётчик, без повторной генерации для получения желаемого распределения.

## Откуда берутся данные

Источники — собственный [генератор](../backend/app/risk/synthetic.py), общий расчёт признаков и демонстрационный [каталог продуктов](../backend/app/products/catalog.py). Это вручную заданные зависимости, а не оценённая на клиентах банка статистика.

Дата отправки и предполагаемой выдачи — 15 января 2025 года, финансовый период — октябрь–декабрь 2024 года. Компании действующие; регистрация предшествует финансовому периоду. Около 10% компаний имеют возраст 4–5 месяцев, остальные 6–240 месяцев. Около 3% имеют нулевую выручку, остальные — 150 000–12 000 000 рублей за три месяца. Расходы составляют 25–120% выручки; при нулевой выручке расходы остаются положительными. Существующие платежи достигают 30% выручки. В 70% случаев исходная просрочка нулевая, иначе 1–89 дней. Сумма, срок, продукт и демонстрационная ставка берутся из каталога.

Вероятность события задаётся плавной формулой. Обозначения: A — возраст в месяцах, R — месячная выручка в рублях, M — маржа, D — существующие платежи/выручка, K — покрытие, O — исходная просрочка в днях:

```text
z = -2.6 - 0.45*log1p(A/12) - 0.25*log1p(R/100000)
    - 1.2*tanh(M) + 1.8*tanh(D) - 0.45*tanh(K/2)
    + 1.5*O/89 + 0.8*exp(-R/100000)
q = sigmoid(z)
p = 1 - (1-q)^n
```

`n` — число договорных ежемесячных платежей, которые после добавления 90 дней ещё попадают в годовой горизонт; для фиксированной даты это `min(term_months, 9)`, реализация использует календарные даты. Неопределённые M/D заменяются нейтральным нулём только при расчёте вероятности внутри генератора. Все коэффициенты придуманы для эксперимента. Порог решения кабинета в генераторе не используется.

Событие разыгрывается с вероятностью p. При событии одна из допустимых дат «платёж + 90 дней» выбирается равномерно; это упрощённое условное распределение времени события, а не постоянный месячный hazard. Без события при сроке менее 12 месяцев явно моделируется окончательное погашение; при более длинном сроке — наблюдение до горизонта. Все сгенерированные метки поэтому известны. Входы и исходы используют отдельные локальные потоки RNG, не меняющие глобальный random state.

## Границы интерпретации

`true_probability` описывает только формулу генератора. Она, будущие события, даты, идентификаторы, метка и решения не входят в признаки модели. Текущий набор не подтверждает качество на реальных компаниях, оценку банковского риска, калибровку вероятности или пригодность порогов кредитной политики. Обучение, SHAP и подключение модели к API остаются отдельными этапами; решения кабинета продолжают работать по демонстрационным правилам.
